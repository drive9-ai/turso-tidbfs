# turso-fs

Native [Turso](https://github.com/tursodatabase/turso) I/O over TiDB Filesystem
(Drive9). SQL, the pager, and the WAL run in the application process; immutable
blocks and a conditional manifest live in FS. No FUSE mount or local database
file is required. The Turso engine is pinned to **0.8.3**.

```text
SQL → Turso pager / WAL → FsIo → FS HTTP API → durable storage
                           └─ demand-loaded block cache
```

## Run

Install Rust and log in with the `ti` CLI. With one active filesystem:

```bash
git clone https://github.com/siddontang/turso-fs.git
cd turso-fs
python3 smoke.py
```

Pass `--fs-id YOUR_FS_ID` or `--profile NAME` to select a filesystem/profile.
Alternatively set `DRIVE9_BASE` and `DRIVE9_API_KEY` in the environment. Hosted
endpoints require HTTPS; HTTP is accepted on loopback only. Tokens generated by
the runner last 30 minutes, are restricted to a unique demo directory, and are
never saved to the repository or reports. Remote demo objects are retained.

For an interactive session with those environment variables set:

```bash
cargo run --release --locked --bin turso-fs -- /experiments/my-agent
```

Enter one complete SQL batch per line; prefix a single query with `?`:

```sql
CREATE TABLE tasks(id INTEGER PRIMARY KEY, title TEXT);
BEGIN; INSERT INTO tasks VALUES(1,'Review plan'); COMMIT;
?SELECT * FROM tasks
?PRAGMA integrity_check
PRAGMA wal_checkpoint(TRUNCATE);
```

EOF closes the connection. Opening that remote directory later recovers the
database. Query rows are JSON arrays of strings. The executable uses
`synchronous=FULL` and disables automatic checkpoints for the experiment.

## Demand reads and writes

Opening a logical file creates only an in-memory descriptor: size and immutable
block references come from `manifest.json`. No data blocks are fetched until
`pread` needs them. Turso's own open/recovery can immediately read its header or
WAL pages; those reads are demand I/O too, not a pre-download of every file.

- Blocks are **32 KiB** and verified with SHA-256 and expected length.
- Repeated reads hit cache. Each file retains up to **64 clean blocks** using LRU
  eviction. Dirty blocks stay pinned until a successful remote sync, so pending
  writes can temporarily exceed that clean-cache bound.
- Partial overwrites fetch only the source blocks they must preserve. Full
  block overwrites never fetch the previous contents.
- Truncate/grow tracks a retained snapshot boundary and zero-fills discarded
  bytes: old immutable data cannot reappear after a truncate and regrow.
- Sync hashes changed/new blocks, preserves untouched block references, uploads
  immutable data, and publishes the manifest last. Unrelated blocks are not read
  during sync. Clean cached blocks can then be evicted safely.

The private directory format remains compatible with the original prototype:

```text
manifest.json          # atomic map of logical database/WAL files
blocks/<sha256>        # immutable blocks; last block can be shorter
```

These objects are adapter storage, not ordinary SQLite files that another
filesystem client can open directly.

## Durability and conflict behavior

A conditional PUT with `X-Dat9-Expected-Revision` publishes all logical file
versions through one manifest. `sync` reports completion only after the server
acknowledges a strictly newer revision. Stale sessions cannot separately
replace another session's database or WAL. Sessions never rebase local mutations
onto another writer's manifest.

Upload failure, a manifest conflict, or an uncertain acknowledgement poisons
the session. Discard its connections and reopen remote state. A failed commit
may already have reached the server: reconcile via SQL before retrying an
application operation. Unpublished blocks are harmless orphans; there is no
block garbage collection yet.

Use **one active session per directory**. This is optimistic conflict detection,
not a distributed lock service. Separate sessions read their own snapshots and
can make a previous writer's next sync fail. File locks coordinate handles only
within one adapter session. Multiple connections sharing one Turso Database use
the engine's normal coordination. Shared multi-process WAL / `.tshm`, MVCC,
partial sync, and Turso Cloud sync are outside this implementation.

## Compare with local disk

```bash
python3 benchmark.py --trials 3
```

Both backends use the **same release-built Turso 0.8.3 engine**, SQL workload,
`FULL` synchronous mode, and 256 KiB pager cache. The local baseline uses Turso's
native Unix filesystem I/O; FS uses the native `FsIo` adapter. Each trial uses
fresh database paths and separate processes for seed, read, and transaction
phases. Execution order alternates between trials.

The 1,024-row fixture has 512-byte payloads. Measurements separate:

- inserts inside a transaction from the bulk transaction's durable commit;
- one point read, a distributed first pass, and repeated cached point reads;
- a full table scan;
- single-row commits and 32-row batch commits, with individual commit samples;
- checkpoint/truncation.

`output/benchmark.json` contains raw timings, per-phase HTTP traffic, machine and
endpoint host, and the median of each trial's average per-operation latency.
`results/` contains a recorded run and an explanation of its limits. The full
scan is reported per row in JSON; compare its total elapsed time for throughput.
These are sequential microbenchmarks, not a concurrency or production capacity
claim. Local OS caches are not dropped. A fresh adapter cache does **not** imply
a cold SSD. Local fsync protects this machine's filesystem; FS sync includes
remote publication and has a different failure boundary. Preparation and final
integrity checks are excluded from per-operation timing.

The runners build release binaries. To reuse a build, set `TURSO_FS_BINARY` for
`smoke.py` or `TURSO_FS_BENCH_BINARY` for `benchmark.py`. `CARGO_TARGET_DIR` is also
supported. Reports and tokens are separate: output files never contain tokens.

## Verification

```bash
cargo test --locked
cargo clippy --locked --all-targets -- -D warnings
cargo fmt --check
python3 smoke.py
```

Unit tests cover lazy reads, cache hits/eviction, full and partial overwrites,
truncate/regrow, incremental sync, real Turso transactions and WAL recovery,
lock ownership, stale writers, corrupt blocks/manifests, failed publication,
and lost acknowledgements. The manual live smoke commits 64 rows, kills the
process with an open uncommitted transaction, recovers in a fresh sandbox,
checks integrity and checkpoint/reopen behavior, and rejects a stale writer with
HTTP 409. It verifies no local database files appeared in its sandbox.

The optional GitHub Actions template is in `ci/github-actions.yml`. To enable
it, publish it as `.github/workflows/check.yml` using a GitHub credential with
`workflow` permission. The credential used for this initial repository upload
cannot install workflows, so Actions is not enabled yet.

## Current limits

- HTTP operations block the calling thread; asynchronous submission is future work.
- 8 MiB per logical file, 8 files, 48 KiB manifest; ASCII database names/root paths.
- HTTP objects must fit the deployment's inline-upload threshold. Redirects and
  multipart upload plans are rejected; credentials are never forwarded to object
  storage URLs.
- No GC, live cross-client coherence, workspace-wide transaction, or LayerFS integration.
- WAL mode is tested; experimental Turso modes are not supported here.
